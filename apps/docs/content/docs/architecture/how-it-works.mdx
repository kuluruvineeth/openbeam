# How it works

OpenBeam follows a five-stage pipeline: **Connect** → **Sync** → **Index** → **Search** → **Answer**. Each stage is designed for durability, correctness, and speed.

## Stage 1: Connect

A user connects a data source through the web UI or CLI. OpenBeam supports OAuth 2.0 (for SaaS tools like Slack, Gmail, Notion) and API key/token authentication (for infrastructure like MQTT, OPC-UA, AWS IoT).

When a connector is created:

1. OAuth flow completes and tokens are encrypted at rest (`encryptedCredentials` in the Connector model)
2. A `Connector` record is created in PostgreSQL with status `CONNECTING`
3. The server registers available resources (channels, folders, repositories) as `ConnectorResource` records
4. A Temporal sync workflow is triggered for the initial full sync

```typescript title="packages/services/src/{connector}/index.ts"
// Each connector implements the sync generator pattern
export async function* fullSync(
  client: ConnectorClient,
  ctx: TransformContext,
  options: SyncOptions
): AsyncGenerator<SyncBatch> {
  let cursor: string | undefined;
  do {
    const page = await client.fetchPage(cursor);
    const documents = page.items.map((item) => transform(item, ctx));
    yield { documents, cursor: page.nextCursor };
    cursor = page.nextCursor;
  } while (cursor);
}
```

## Stage 2: Sync

All sync work runs as Temporal workflows. Temporal provides durable execution: if the worker crashes mid-sync, the workflow resumes from the last checkpoint.

### Activity chain

| Step | Activity | What happens |
|------|----------|-------------|
| 1 | `validateConnection` | Verify connector status, check token freshness, refresh if expired |
| 2 | `fetchBatch` | Call the connector API with a cursor, handle pagination and rate limits |
| 3 | `transformBatch` | Convert API responses to `GenericDocument` format via the connector's transformer |
| 4 | `indexDocuments` | Bulk feed documents to Vespa with chunking and embedding generation |
| 5 | `completeSyncJob` | Update `SyncHistory` with metrics (docs added, updated, deleted, timing) |

### Fencing protocol

To prevent stale writes when multiple sync workflows run concurrently, every sync acquires a monotonic fence token before writing:

```typescript
const fenceToken = await fence.acquireFence(connectorId);
try {
  await indexDocuments(batch, fenceToken);
} finally {
  await fence.releaseFence(connectorId, fenceToken);
}
```

### Error handling

| Error type | Behavior |
|------------|----------|
| **Auth expired** | Non-retryable. Connector marked `AUTH_EXPIRED`, user notified |
| **Rate limited** | Retryable with backoff from `Retry-After` header |
| **Transient failure** | Automatic retry with exponential backoff (up to 3 retries) |
| **Permanent failure** | Document sent to `SyncDeadLetter` for manual review |

### History management

Temporal workflows accumulate event history. To prevent memory bloat, sync workflows call `continueAsNew` when history exceeds 10,000 events, carrying forward only the cursor and sync state.

### Incremental sync

After the initial full sync, subsequent syncs are incremental. The `SyncCursor` model stores per-resource cursors (timestamps, API cursors, or sync tokens) so only changed documents are fetched.

| Cursor type | Used by | Example |
|-------------|---------|---------|
| `timestamp` | Gmail, Slack | `lastSyncedAt: 2026-01-15T10:30:00Z` |
| `cursor` | Notion, Linear | `next_cursor: abc123` |
| `sync_token` | Google Drive | `startPageToken: 456` |

## Stage 3: Index

Documents are indexed into Vespa as `GenericDocument` records. This is the universal schema that all connectors produce:

```typescript title="packages/vespa/src/schemas.ts"
interface GenericDocument {
  id: string;
  connector_id: string;
  connector_type: string;
  team_id: string;
  workspace_id: string;
  external_id: string;
  document_type: string;
  title: string;
  content: string;
  content_embedding?: number[];         // x[1536] dense vector
  title_embedding?: number[];           // x[1536] dense vector
  embedding?: number[];                 // x[1024] v2 dense vector
  sparse_embedding?: Record<string, number>; // learned sparse weights
  author_name?: string;
  author_email?: string;
  created_at: number;
  updated_at: number;
  status?: string;
  priority?: string;
  labels?: string[];
  url?: string;
  access_control?: string[];
  is_public: boolean;
  entity_ids?: string[];
  topics?: string[];
  authority_score?: number;
  quality_score?: number;
  metadata?: Record<string, unknown>;
}
```

The full schema has 100+ fields covering collaboration (contributor_ids, assignee_ids), document structure (chunk_index, section_path), engagement metrics (view_count, reaction_count), and knowledge graph links (entity_ids, topics). See the [Search](/docs/search) section for the complete field reference.

### Processing pipeline

For files (PDFs, DOCX, XLSX), the worker sends them through the Python engine for text extraction:

1. **Download** -- File fetched from source and stored in S3/MinIO
2. **Parse** -- Python engine extracts text (Unstructured library)
3. **Chunk** -- Text split into overlapping chunks (512 tokens, 64 token overlap)
4. **Embed** -- Each chunk gets a vector embedding
5. **Index** -- Chunks indexed in Vespa with metadata

The `IndexedFile` model tracks processing status through states: `PENDING` → `DOWNLOADING` → `PARSING` → `INDEXING` → `INDEXED`.

## Stage 4: Search

When a user searches, OpenBeam runs hybrid search combining keyword matching (BM25) and semantic similarity (vector search) in a single Vespa query.

### Latency budget (200ms p99)

| Stage | Budget | Operation |
|-------|--------|-----------|
| Query analysis | 10ms | Intent classification, entity extraction |
| Permission resolution | 5ms | Pre-computed permission group lookup |
| Vespa hybrid search | 100ms | Parallel BM25 + semantic vector query |
| Re-ranking | 50ms | LTR model scoring (trained on click data) |
| Personalization | 15ms | User profile weight application |
| Response + buffer | 20ms | Serialization, network variance |

### Permission filtering

Permissions are pre-computed and synced from source systems into the `DocumentPermission` table. At query time, the user's permission group IDs are resolved in under 5ms and passed as a filter to Vespa. Users only see documents they can access in the original tool.

```text
User → GroupMembership → permission_group_ids → Vespa filter
```

### Search quality feedback loop

Every search impression is logged (`SearchImpression`), and clicks are tracked (`SearchClick`) with dwell time. This data trains the LTR (Learning to Rank) re-ranking model per team, which improves result quality over time.

## Stage 5: Answer

For AI-powered answers, the search results become context for a RAG (Retrieval-Augmented Generation) pipeline:

1. **Retrieve** -- Top-k documents from hybrid search (same as Stage 4)
2. **Chunk selection** -- Most relevant chunks selected based on query similarity
3. **Ground** -- LLM generates an answer using only retrieved chunks as context
4. **Cite** -- Response includes inline citations linking back to source documents
5. **Verify** -- Grounding score computed to measure answer faithfulness

The AI pipeline uses the Vercel AI SDK with support for Claude, GPT, and Gemini. Each interaction is tracked in `RAGInteraction` with token counts, latency, and grounding scores.

### Agent canvas

For multi-step workflows, the Agent Canvas provides a visual builder where users compose agents from tools. Agents can:

- Search across connected sources
- Analyze and summarize documents
- Execute multi-step reasoning chains
- Request human approval before taking actions
- Run on schedules or in response to events

Agent executions are Temporal workflows, providing the same durability and visibility guarantees as sync workflows.
