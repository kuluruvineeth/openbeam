# Architecture

## Request Flow

```
1. Platform sends webhook POST to /webhooks/{platform}
2. Adapter verifies signature (HMAC-SHA256, JWT, or Ed25519)
3. Adapter parses raw event into UnifiedMessage
4. Rate limiter checks per-user and per-team limits
5. resolveIdentity() looks up BotUserLink -> teamId + userId
6. If unlinked -> sendLinkPrompt() with magic link
7. Adapter sends typing indicator (WhatsApp: typing_indicator API, Telegram: sendChatAction)
8. Router detects intent: greeting, command prefix, regex pattern, or fallback to ask
9. Handler calls @openbeam/services and builds BotResponse with citations + follow-ups
10. Adapter calls platform renderer (Block Kit / Embed / Adaptive Card / HTML / Interactive)
11. Adapter sends platform-native payload back via platform API
```

## Renderer Architecture

Each platform has a dedicated renderer that converts a `BotResponse` into a platform-native payload:

| Platform | Renderer | Output |
|----------|----------|--------|
| Slack | `renderSlack()` | `{ blocks: Block[], text: string }` |
| Discord | `renderDiscord()` | `{ type, data: { embeds, components } }` |
| Telegram | `renderTelegram()` | `{ text: string, parse_mode: "HTML", reply_markup? }` |
| Teams | `renderTeams()` | `{ type: "message", attachments: [AdaptiveCard] }` |
| WhatsApp | `renderWhatsApp()` | Interactive (list/button) or text payload |

Renderers handle:
- Response type routing (search results, answers, experts, actions, errors)
- Platform-specific escaping (HTML entities, mrkdwn, etc.)
- Citation formatting (context blocks, footers, FactSets, inline text)
- Follow-up suggestion buttons (action blocks, component rows, inline keyboards, reply buttons)
- Truncation to platform character limits

## Adding a New Platform

1. Create `apps/bot/src/adapters/{platform}.ts` implementing `PlatformAdapter`
2. Create `apps/bot/src/renderers/{platform}.ts` with a `render{Platform}()` function
3. Add platform to `BotPlatformSchema` in `packages/types/src/bot/platforms.ts`
4. Add platform config to `PLATFORM_CONFIGS` with character limits and capabilities
5. Register the adapter in `apps/bot/src/adapters/index.ts`
6. Add the webhook route in `apps/bot/src/routes.ts`
7. Export from `apps/bot/src/renderers/index.ts`
8. Add tests in `apps/bot/__tests__/renderers/{platform}.test.ts`

## Key Design Decisions

**Adapter Registry Pattern** — adapters register themselves via `registerAdapter()`. Adding a new platform doesn't modify existing adapter code.

**Renderers over formatters** — each platform gets a dedicated renderer producing native payloads (Block Kit JSON, Embed objects, Adaptive Cards) instead of a lowest-common-denominator string formatter. This means Slack gets real Block Kit, Discord gets colored embeds, Teams gets Adaptive Cards.

**Separate from apps/server** — the bot has different scaling needs, different dependencies (platform SDKs), and different deploy lifecycle than the main API server.

**Delegates to existing services** — the Slack adapter calls `verifySlackSignature` and `parseSlackEvent` from `@openbeam/services`. Handlers call `hybridSearch`, `ragAnswer`, `dispatchAction`. No duplicated business logic.

**Zod schemas for external data** — all adapters validate incoming webhook payloads with Zod schemas. No `any` types, no unchecked casts on untrusted data.

**Citations as first-class data** — `BotResponse` includes structured `Citation[]` with index, title, URL, and snippet. Renderers format these natively per platform (Slack context blocks, Discord footers, Teams FactSets, Telegram HTML links, WhatsApp inline text).
