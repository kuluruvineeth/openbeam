# Encryption

OpenBeam encrypts sensitive data at rest using AES-256-GCM and enforces TLS for data in transit. This page covers what gets encrypted, how keys are managed, and the security properties of each mechanism.

## What Gets Encrypted

All third-party credentials stored in PostgreSQL are encrypted before write and decrypted on read. Plaintext credentials never touch disk.

| Data | Storage | Encryption |
|------|---------|------------|
| OAuth access tokens | PostgreSQL | AES-256-GCM |
| OAuth refresh tokens | PostgreSQL | AES-256-GCM |
| API secrets (connector) | PostgreSQL | AES-256-GCM |
| Webhook signing secrets | PostgreSQL | AES-256-GCM |
| Service account keys | PostgreSQL | AES-256-GCM |
| User session tokens | PostgreSQL | Stored as-is (random bytes, no secret content) |
| API keys | PostgreSQL | Argon2 hash (one-way, not reversible) |

<Callout type="warn">
  Session tokens and API keys are not encrypted with AES-256-GCM because they do not need to be recovered. Session tokens are opaque random bytes. API keys are stored as irreversible Argon2 hashes.
</Callout>

## AES-256-GCM at Rest

### Algorithm Properties

| Property | Value |
|----------|-------|
| Algorithm | AES-256-GCM (Galois/Counter Mode) |
| Key size | 256 bits (32 bytes) |
| IV size | 96 bits (12 bytes), randomly generated per encryption |
| Auth tag size | 128 bits (16 bytes) |
| Mode | Authenticated encryption (confidentiality + integrity) |

AES-256-GCM provides both confidentiality and authenticity. The authentication tag ensures that ciphertext cannot be modified without detection -- any tampering causes decryption to fail.

### Encryption Flow

```text
Encrypt:
  1. Generate 12-byte random IV (crypto.randomBytes(12))
  2. Create AES-256-GCM cipher with ENCRYPTION_KEY + IV
  3. Encrypt plaintext → ciphertext
  4. Extract 16-byte auth tag from cipher
  5. Store: IV (12 bytes) + ciphertext + auth tag (16 bytes)

Decrypt:
  1. Extract IV (first 12 bytes) from stored value
  2. Extract auth tag (last 16 bytes) from stored value
  3. Extract ciphertext (middle bytes)
  4. Create AES-256-GCM decipher with ENCRYPTION_KEY + IV
  5. Set auth tag on decipher
  6. Decrypt ciphertext → plaintext
  7. If auth tag verification fails → throw error (data tampered)
```

### Implementation

```typescript
import { randomBytes, createCipheriv, createDecipheriv } from "node:crypto";

const ALGORITHM = "aes-256-gcm";
const IV_LENGTH = 12;
const TAG_LENGTH = 16;

function encrypt(plaintext: string, key: Buffer): string {
  const iv = randomBytes(IV_LENGTH);
  const cipher = createCipheriv(ALGORITHM, key, iv);

  const encrypted = Buffer.concat([
    cipher.update(plaintext, "utf8"),
    cipher.final(),
  ]);

  const tag = cipher.getAuthTag();

  // IV + ciphertext + auth tag → single base64 string
  return Buffer.concat([iv, encrypted, tag]).toString("base64");
}

function decrypt(encoded: string, key: Buffer): string {
  const data = Buffer.from(encoded, "base64");

  const iv = data.subarray(0, IV_LENGTH);
  const tag = data.subarray(data.length - TAG_LENGTH);
  const ciphertext = data.subarray(IV_LENGTH, data.length - TAG_LENGTH);

  const decipher = createDecipheriv(ALGORITHM, key, iv);
  decipher.setAuthTag(tag);

  return decipher.update(ciphertext) + decipher.final("utf8");
}
```

### Storage Format

Encrypted values are stored as a single base64-encoded string containing all three components:

```text
base64( IV[12] + ciphertext[variable] + authTag[16] )
```

This makes encrypted fields portable -- they can be backed up, restored, and moved between databases without losing the IV or auth tag.

## Key Management

### ENCRYPTION_KEY

The encryption key is provided via the `ENCRYPTION_KEY` environment variable: 64 hexadecimal characters representing 32 bytes.

```bash
# Generate a secure encryption key
openssl rand -hex 32
# Output: a1b2c3d4e5f6...  (64 hex characters)
```

<Callout type="warn">
  The encryption key is the single most sensitive secret in your deployment. If it is lost, all encrypted credentials become unrecoverable. If it is compromised, all stored credentials are exposed. Store it in a secret manager, not in a config file.
</Callout>

### Key Derivation

The hex string is decoded to a 32-byte `Buffer` at startup:

```typescript
const key = Buffer.from(process.env.ENCRYPTION_KEY, "hex");
// 64 hex chars → 32 bytes → 256-bit AES key
```

If the key is missing or malformed (not 64 hex characters), the server refuses to start.

### Key Rotation

OpenBeam does not currently support automatic key rotation. To rotate the encryption key:

1. Take a database backup
2. Write a migration script that decrypts all credentials with the old key and re-encrypts with the new key
3. Update `ENCRYPTION_KEY` in all service environments
4. Restart all services
5. Verify connector syncs still work (they will fail if decryption fails)

<Callout type="info">
  Key rotation is a manual process. Plan for it as part of your incident response procedures.
</Callout>

## Cookie Security

Session cookies carry the configuration described in the [Authentication](/docs/security/authentication) page. The security-relevant flags:

| Flag | Value | Protection |
|------|-------|------------|
| `httpOnly` | `true` | JavaScript cannot read the cookie (XSS mitigation) |
| `secure` | `true` | Cookie only transmitted over HTTPS (man-in-the-middle mitigation) |
| `sameSite` | `lax` | Cookie not sent on cross-origin POST requests (CSRF mitigation) |

### httpOnly

The `httpOnly` flag prevents client-side JavaScript from accessing the cookie via `document.cookie`. Even if an XSS vulnerability exists, the attacker cannot exfiltrate the session token through JavaScript.

### secure

The `secure` flag ensures the cookie is only sent over HTTPS connections. On plain HTTP, the browser will not include the cookie in the request, preventing session tokens from being transmitted in cleartext.

### sameSite=lax

The `lax` setting allows the cookie to be sent on top-level navigations (clicking a link to your site) but not on cross-origin form submissions or AJAX requests. This prevents CSRF attacks while maintaining normal navigation behavior.

### Domain Configuration

The cookie domain is derived from the `COOKIE_DOMAIN` environment variable. For cross-origin deployments where the frontend (`app.example.com`) and API (`api.example.com`) are on different subdomains, set `COOKIE_DOMAIN=.example.com` to allow the cookie to be shared.

## Transport Security

### TLS

All production traffic must use TLS 1.2 or higher. TLS termination typically happens at the reverse proxy (nginx, Caddy, or cloud load balancer) in front of the application services.

Internal communication between containers on the Docker network uses plain HTTP. This is acceptable because the Docker network is isolated and not exposed to the public internet.

```text
Internet ──[TLS]──▶ Reverse Proxy ──[HTTP]──▶ Server (:3000)
                                   ──[HTTP]──▶ Web (:3001)
```

### CORS

The API server restricts cross-origin requests to the configured frontend URL:

| Header | Value |
|--------|-------|
| `Access-Control-Allow-Origin` | `WEB_URL` (e.g., `https://app.example.com`) |
| `Access-Control-Allow-Credentials` | `true` |
| `Access-Control-Allow-Methods` | `GET, POST, PUT, DELETE, OPTIONS` |
| `Access-Control-Allow-Headers` | `Content-Type, Authorization` |

<Callout type="warn">
  Never set `Access-Control-Allow-Origin` to `*` in production. This would allow any website to make authenticated requests to your API using the user's session cookie.
</Callout>

### Temporal mTLS

Temporal worker-to-server communication supports mutual TLS (mTLS) for environments that require it. In mTLS mode, both the worker and the Temporal server present certificates, ensuring bidirectional authentication.

| Configuration | Variable | Description |
|---------------|----------|-------------|
| Client certificate | `TEMPORAL_TLS_CERT` | PEM-encoded client certificate |
| Client key | `TEMPORAL_TLS_KEY` | PEM-encoded client private key |
| CA certificate | `TEMPORAL_TLS_CA` | Certificate authority for server verification |

In the default Docker Compose deployment, Temporal runs on the internal network without TLS. Enable mTLS when deploying Temporal on a separate network or using Temporal Cloud.
