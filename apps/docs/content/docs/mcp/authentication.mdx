# Authentication

The OpenBeam MCP server authenticates every request before registering tools or returning data. Authentication determines which team's data is accessible and which tools are available based on assigned scopes.

## Authentication Methods

OpenBeam supports two authentication methods. Most MCP clients support both.

### OAuth 2.1 with PKCE (Recommended)

OpenBeam implements the standard MCP OAuth specification. Clients that support OAuth (Claude Desktop, Cursor, Codex, and others) can discover the auth server automatically:

```text
GET https://api.openbeam.dev/.well-known/oauth-authorization-server
```

This returns the authorization, token, and registration endpoints. The flow uses `authorization_code` grant with `S256` PKCE. No client secret is required (`token_endpoint_auth_methods_supported: ["none"]`).

When you add OpenBeam as a remote MCP server, the client handles the OAuth flow automatically — you sign in to OpenBeam, authorize the connection, and the client receives a scoped token.

```http
Authorization: Bearer op_access_xxxxxxxxxxxx
```

### API Key Authentication

For clients that do not support OAuth, or for headless/CI environments, use an API key. Generate one in the OpenBeam dashboard at **Settings > API Keys**.

```http
Authorization: Bearer op_live_xxxxxxxxxxxx
```

API key prefixes: `op_live_` for production, `op_test_` for sandbox. The server also accepts keys via the `Mcp-Api-Key` header or the `api_key` query parameter as fallbacks.

## API Key Format

| Environment | Prefix | Example |
|-------------|--------|---------|
| Production | `op_live_` | `op_live_a1b2c3d4e5f6g7h8` |
| Sandbox | `op_test_` | `op_test_x9y8z7w6v5u4t3s2` |

Production keys access real team data. Sandbox keys are scoped to test environments and will not trigger real syncs or modify production connectors.

## Getting an API Key

<Steps>
<Step>

### Open the dashboard

Navigate to **Settings** in the OpenBeam web application.

</Step>
<Step>

### Create a key

Go to **API Keys** and click **Create**. Assign a descriptive name and select the scopes this key should grant.

</Step>
<Step>

### Copy the key

The full key is shown once. Copy it immediately and store it in a secure location (password manager, environment variable, or secrets vault).

</Step>
</Steps>

<Callout type="warn">
API keys are shown only at creation time. If you lose a key, revoke it and create a new one.
</Callout>

## Scopes and Permissions

Every API key (and OAuth token) is assigned one or more scopes. Scopes control which MCP tools are registered when the server initializes. If a key lacks a required scope, the corresponding tools are not exposed at all.

| Scope | Access | Tools Gated |
|-------|--------|-------------|
| `search.read` | Search documents and people | `search_documents`, `search_people`, `ask_question` |
| `connectors.read` | List and inspect connectors | `connector_list`, `connector_get`, `connector_health`, `connector_actions_list` |
| `connectors.write` | Setup, configure, disconnect connectors | `connector_setup`, `connector_configure`, `connector_disconnect`, `connector_action_execute` |
| `sync.read` | View sync status and history | `sync_status`, `sync_history` |
| `sync.write` | Trigger sync jobs | `sync_trigger` |
| `teams.read` | View team info and members | `team_info`, `team_members` |
| `context.read` | Search and read context database | `context_search`, `context_read` |
| `admin:*` | Full access (all scopes) | All tools |

The `admin:*` scope is a wildcard that grants access to every tool regardless of individual scope assignments.

<Callout type="info">
Scopes are normalized internally. Both `connectors.read` and `connectors:read` are accepted and treated identically.
</Callout>

## Tool Annotations

Each tool carries an annotation set that describes its behavior to the MCP client. Clients can use these hints to warn users before executing destructive operations or to distinguish reads from writes.

| Annotation | `readOnlyHint` | `destructiveHint` | `idempotentHint` | Used By |
|------------|---------------|-------------------|-------------------|---------|
| `READ_ONLY` | `true` | `false` | `true` | Search, list, status tools |
| `WRITE` | `false` | `false` | `false` | Create, update, configure tools |
| `DESTRUCTIVE` | `false` | `true` | `true` | Disconnect, delete tools |

## Security Best Practices

<Cards>
  <Card title="Rotate keys regularly" description="Revoke and recreate API keys on a schedule. Avoid long-lived keys in production environments." />
  <Card title="Use scoped keys" description="Grant only the scopes each integration needs. A monitoring dashboard only needs search.read and connectors.read." />
  <Card title="Never commit keys" description="Store keys in environment variables or a secrets manager. Never check them into version control." />
  <Card title="Audit usage" description="Review API key activity in the dashboard. Revoke any key that shows unexpected access patterns." />
</Cards>

### Environment Variable Example

```bash
# .env (never committed)
OPENBEAM_API_KEY=op_live_a1b2c3d4e5f6g7h8
```

```json
{
  "mcpServers": {
    "openbeam": {
      "url": "https://api.openbeam.work/mcp",
      "headers": {
        "Authorization": "Bearer ${OPENBEAM_API_KEY}"
      }
    }
  }
}
```

## Error Responses

When authentication fails, the server returns a `401` status with a `WWW-Authenticate` header pointing to the OAuth resource metadata endpoint.

```json
{
  "error": "unauthorized",
  "error_description": "Bearer token required. Provide an API key via the Authorization header."
}
```

Common causes:

| Symptom | Cause | Fix |
|---------|-------|-----|
| `401 unauthorized` | Missing or invalid token | Verify the key starts with `op_live_` or `op_access_` |
| No tools visible | Key lacks required scopes | Check scope assignments in **Settings > API Keys** |
| Partial tool list | Key has limited scopes | Add missing scopes or use an `admin:*` key for full access |
